The player enters a tile (initializing the game loop, the player spawns on the start tile; thereafter, the start tile is never used again; this is the only difference from the start). 
1) The tile is marked as "ACTIVE". [**TileStateManager.gd**: `_set_tile_state()`]
2) The tile that they previously came from is marked "PREVIOUS". [**TileStateManager.gd**: `_set_tile_state()`]
3) the game checks to see where the active tile's exits are. [**TileManager.gd**: `_get_tile_doors()` - **NOTE**: Current implementation uses door detection on tile scenes]
4) At every exit, a "CONNECTING" tile is considered for spawning. (The exception is the tile that is connected to entrance that the player came through, which is connected to the previous tile - this tile is skipped). [**TileManager.gd**: `_spawn_tile_connections()`]

5) First, the program checks to see the world location (the code may suggest that the world is a 10x10 grid, I've decided to change it to a 7x7 grid - so the grit should cover a square area with corners at (3,3) and (-3,-3).) [**TileManager.gd**: `_apply_world_wrapping()` - **IMPLEMENTED**: Uses 7x7 grid wrapping]
5a) If there is a "PERMENANT" tile that has been laid down in a previous run that should be at that location, it is the tile that is connected. (If the world position is outside of the 7x7 grid, the program needs to wrap back around to the other extreme - so instead of checking for a tile at (4,3), the program checks if there is a tile at -3,3, and if there is, uses that - and subsequent movements into the positive x continue to follow this). [**TileManager.gd**: `_apply_world_wrapping()` and `_get_permanent_tile_at_position()`]
5b) If there is no permanent tile there, a tile is randomly selected from all available tiles (located in the res:\scenes\tiles folder). [**TileManager.gd**: `_select_random_tile()`]
6) In either case, the tile is spawned there (offset 20 units from the center of the active tile). [**TileManager.gd**: `_spawn_tile_at_position()`]
7) The connecting tile is then assessed for number of doors available. [**TileManager.gd**: `_get_tile_doors()`]
8) The tile is rotated so that one of the available doors on the connecting tile lines up with the door on the active tile that it was spawned near. [**TileManager.gd**: `_rotate_tile_to_connect()` - **NOTE**: Current implementation may need verification of door alignment logic]
9) Once positioned, all avaiable item drop points (available in the Maze/ItemSpawn node) on the connecting tile are placed in an array and randomly sorted. [**SpawnManager.gd**: `_get_spawn_points()` - **FIXED**: Now checks Maze/ItemSpawn and Maze/EntitySpawn nodes]
10)  The tile's position is checked to whether the player died on that tile during a previous run, and whether that previous run's inventory is still available. [**SpawnManager.gd**: `process_tile_spawning()` calls **GameStateManager.gd**: `get_unused_death_at_position()`]
10a) If both conditions are met, then a backpack containing that inventory is dropped at the first item drop point and the item placement loop breaks. [**SpawnManager.gd**: `_spawn_backpack_at_death()`]
10b) If the loop continues, available items are randomly sorted (only the 5 currently lowest numbered notes are available, plus all other objects that have not been picked up yet). Each drop point has a 3% base chance of having an item present at any given drop point. However, once one object has dropped on this tile, the loop breaks. [**SpawnManager.gd**: `_spawn_items()` - **IMPLEMENTED**: Uses 3% spawn chance, breaks after first item]
11)  All available entity postions (Maze/EntitySpawn) on the connecting tile are placed in an array and randomly sorted. [**SpawnManager.gd**: `_get_spawn_points()` - **FIXED**: Now properly detects Maze/EntitySpawn]
12)  If a previous player's inventory was dropped here, an 'Effigy' is spawned at the first entity point and the entity placement loop breaks. Else, each spawn point has a 4% chance of spawning an entity. The type of entity changes based on Sanity - Stalkers have a base 90% chance of spawning - current sanity level (sanity goes up to 100, so when the game first starts, and sanity is high (greater than 90%), there is no chance of a stalker spawning - negative percentages counts as no spawn chance). If a Stalker is not spawned, then an Effigy spawns. Once one entity has spawned, the entity loop breaks. [**EnemyManager.gd**: `spawn_enemy()` and **EffigyManager.gd**: `spawn_effigy_at_death_location()` - **NOTE**: Entity spawning logic needs review for 4% chance and sanity-based spawning]
13)  Once all tiles for any avialable door is placed for the active tile, the previous tile's connecting tiles are 'cleaned up'. If there are any entites or unpicked up items on these tiles, they are also cleaned up. The only tiles remaining in the world should be the Active tile, the Previous tile, and between 0 and 3 connecting tiles. [**TileManager.gd**: `cleanup_old_tiles()` - **NOTE**: Cleanup logic needs verification]
14)  All entrance/exit markers on the active tile are 'inactivated', as they will no longer be used while the player is on this tile. The previous tile's entrance/exit markers are reactivated. [**TileManager.gd**: door management - **NOTE**: Implementation needs verification]
15)  If, while the player is on the active tile, they pick up an item, the item is added to the player's inventory and removed from the array of items that can be dropped. If they pick up the inventory of a previous run, those items (and those items only - there may be other inventory drops that still exist out there). [**PlayerInventory.gd**: `add_item()` and **ItemManager.gd**: item availability tracking]
16)  If the player dies on the active tile, then the location on the world map is logged, along with the inventory (which is then added to the dropped inventory list), type of death (sanity loss [fragmentation], stalker death [consumed], the run was prematurely terminated [harvested], etc - these are the only three I can think of off the top of my head). ##Stalker Behavior [**Stalker.gd**: `_check_state_transitions()` and `_update_movement()`]
A stalker will always know where the player is on the tile, moving towards them across the shortest path possible (if they are moving) while avoiding moving through walls. [**Stalker.gd**: `_update_navigation()` and `_update_movement()`]
If the stalker touches the player, the player dies (consumed) [**Stalker.gd**: `_kill_player()` when collision detected]
1) At greater than 70% Sanity, Stalker is idle, turning bodily to watch the player. [**Stalker.gd**: `StalkerState.PATROLLING` - **IMPLEMENTED**: Correctly transitions based on sanity thresholds]
2) With less than 70% but greater than 50%, the Stalker will begin moving toward the player at ~half the player's normal speed, stopping 2 meters from the player to watch them. [**Stalker.gd**: `StalkerState.HUNTING` with reduced speed - **IMPLEMENTED**: Uses sanity-based speed modifiers]
3) With less than 50% but greater than 30%, the Stalker will no longer stop 2 meters from the player - they will actively try to touch the player. [**Stalker.gd**: `StalkerState.HUNTING` with full pursuit - **IMPLEMENTED**: Removes distance stopping behavior]
4) At less than 30% sanity, the stalker will begin to move at ever greater speeds, up to matching player's speed at 10% sanity. [**Stalker.gd**: `StalkerState.HUNTING` with increasing speed - **IMPLEMENTED**: Speed increases as sanity decreases below 30%]
